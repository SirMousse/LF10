--------------------------------------------------
QUEST 4 - DER PRIMARY KEY
--------------------------------------------------

Du hast bereits mehrfach die Spalte "id" verwendet.

Aber warum ist sie so wichtig?

In unserer Tabelle steht:

id INT PRIMARY KEY


PRIMARY KEY bedeutet:

Der Wert identifiziert einen Datensatz eindeutig.


Beispiel:

id = 1

darf nur einmal vorkommen.


Folgendes wäre also problematisch:

id | name
1  | Arin
1  | Gandalf


Die Datenbank könnte nicht eindeutig erkennen,
welcher Datensatz gemeint ist.


SQL-Wissen:

Ein PRIMARY KEY sollte:

- eindeutig sein
- nicht NULL sein
- einen Datensatz eindeutig identifizieren


--------------------------------------------------
QUEST 5 - DER FOREIGN KEY
--------------------------------------------------

Unsere Tabelle "auftraege" besitzt:

abenteurer_id


Diese Spalte verweist auf:

abenteurer.id


Eine solche Verbindung kann mit einem FOREIGN KEY abgesichert werden.


Beispiel:

CREATE TABLE auftraege (
    id INT PRIMARY KEY,
    titel VARCHAR(100),
    schwierigkeit VARCHAR(20),
    belohnung INT,
    abenteurer_id INT,
    FOREIGN KEY (abenteurer_id)
        REFERENCES abenteurer(id)
);


SQL-Wissen:

PRIMARY KEY:

Identifiziert einen Datensatz.


FOREIGN KEY:

Verweist auf einen Datensatz in einer anderen Tabelle.


Dadurch entstehen Beziehungen zwischen Tabellen.


--------------------------------------------------
QUEST 6 - DAS GEHEIMNIS DES LEFT JOIN
--------------------------------------------------

Du kennst bereits:

JOIN


Ein normaler JOIN zeigt nur Datensätze,
für die eine passende Verbindung existiert.

Aber was passiert mit Abenteurern,
die noch keinen Auftrag haben?


Hier kommt LEFT JOIN ins Spiel.


Beispiel:

SELECT abenteurer.name, auftraege.titel
FROM abenteurer
LEFT JOIN auftraege
ON abenteurer.id = auftraege.abenteurer_id;


LEFT JOIN bedeutet:

Zeige ALLE Datensätze der linken Tabelle.

Auch wenn kein passender Datensatz in der rechten Tabelle existiert.


In diesem Beispiel ist:

abenteurer = linke Tabelle
auftraege = rechte Tabelle


Hat ein Abenteurer keinen Auftrag, steht beim Auftrag möglicherweise:

NULL


AUFGABE:

Zeige mit LEFT JOIN:

name
klasse
titel

für alle Abenteurer.

Auch Abenteurer ohne Auftrag sollen angezeigt werden.

--------------------------------------------------
QUEST 8 - HAVING
--------------------------------------------------

Der Gildenmeister möchte wissen:
Welche Abenteurer haben MEHR ALS EINEN Auftrag?


Wir kennen bereits:

GROUP BY


Beispiel:

SELECT abenteurer.name, COUNT(auftraege.id)
FROM abenteurer
JOIN auftraege
ON abenteurer.id = auftraege.abenteurer_id
GROUP BY abenteurer.name;


Aber wie filtern wir das Ergebnis von COUNT()?


Dafür gibt es:

HAVING


Beispiel:

SELECT abenteurer.name, COUNT(auftraege.id)
FROM abenteurer
JOIN auftraege
ON abenteurer.id = auftraege.abenteurer_id
GROUP BY abenteurer.name
HAVING COUNT(auftraege.id) > 1;


SQL-Wissen:

WHERE filtert einzelne Datensätze.

HAVING filtert Gruppen.


Merksatz:

WHERE kommt normalerweise vor GROUP BY.

HAVING kommt nach GROUP BY.


--------------------------------------------------
QUEST 9 - DIE UNTERABFRAGE
--------------------------------------------------

Der Gildenmeister stellt eine schwierige Frage:

Welche Abenteurer besitzen mehr Gold als der durchschnittliche Abenteurer?


Zuerst können wir den Durchschnitt berechnen:

SELECT AVG(gold)
FROM abenteurer;


Aber wir können diese Abfrage auch in eine andere Abfrage einbauen.


Beispiel:

SELECT name, gold
FROM abenteurer
WHERE gold > (
    SELECT AVG(gold)
    FROM abenteurer
);


Das nennt man:

Unterabfrage

oder:

Subquery


Die innere Abfrage berechnet zuerst:

SELECT AVG(gold)
FROM abenteurer;


Danach verwendet die äußere Abfrage dieses Ergebnis.


AUFGABE:
